# Канал результата сервера: буфер, остановка и утечка горутины

В `cmd/api/main.go` HTTP-сервер запущен в отдельной горутине, а результат `ListenAndServe` передаётся через канал:

```go
serveErr := make(chan error, 1)
go func() { serveErr <- server.ListenAndServe() }()

select {
case <-signalCtx.Done():
    // Затем вызывается server.Shutdown(...).
case err := <-serveErr:
    // Обрабатывается ошибка сервера.
}
```

`select` выбирает **одну** готовую ветку. Если выбран сигнал, ветка чтения из `serveErr` позже сама собой не выполнится. После вызова `Shutdown` метод `ListenAndServe` возвращает `http.ErrServerClosed`, и горутина пытается отправить эту ошибку в канал. `Shutdown` ждёт завершения активных HTTP-запросов, но не ждёт отправки в наш канал: это отдельная операция, добавленная в горутину приложения.

## Канал без буфера

При `serveErr := make(chan error)` отправка и чтение должны встретиться. Если `select` уже выбрал сигнал и дальнейшего чтения нет, горутина застрянет на `serveErr <- err`. Это не удерживает `main` от возврата: Go-программа завершается, когда завершается её главная горутина, даже если другие горутины ещё работают или заблокированы.

Если аналогичный `run()` вызван из теста или из процесса, который продолжает работать, застрявшая горутина останется в памяти. Такая ситуация называется **утечкой горутины**. Она удерживает свой стек, ссылку на канал и другие достижимые из неё объекты. Потеря всех *внешних* ссылок на канал не помогает: заблокированная горутина сама всё ещё ссылается на него. Сборщик мусора не завершает горутины, ожидающие операции с каналом. При повторении сценария число таких горутин будет расти.

## Канал с буфером на одно значение

При `serveErr := make(chan error, 1)` в канале есть место для одного результата. Отправка `serveErr <- err` помещает **значение ошибки** в буфер и сразу завершается, даже если читателя нет. В буфере находится значение, а не ожидающее чтение. После отправки горутина доходит до конца функции и завершается.

Если значение не прочитали и на канал больше не осталось ссылок, сборщик мусора может освободить канал вместе с буфером и хранящимся в нём значением. Пока ссылка на канал сохраняется, значение тоже остаётся доступным. Если буфер заполнен, следующая отправка снова будет ждать свободного места или читателя. Здесь ёмкости `1` достаточно: горутина отправляет ровно один результат.

| После выбора ветки сигнала | Канал без буфера | Канал с буфером `1` |
| --- | --- | --- |
| Есть ли читатель результата? | Нет | Нет |
| Завершится ли отправка? | Нет, горутина ждёт читателя | Да, результат попадает в буфер |
| Завершится ли горутина сервера? | Нет, пока никто не прочитает канал | Да |
| Что будет после возврата `main`? | Процесс завершится вместе с горутиной | Процесс завершится; непрочитанное значение исчезнет вместе с ним |

В текущем `cmd/api/main.go` различие почти не заметно извне: после остановки сервера `run()` возвращается, затем завершается весь процесс. Буфер позволяет горутине завершиться самостоятельно до выхода процесса. Он особенно полезен, когда вызывающий код или тест продолжает работу после `run()`.

## Вариант без буфера с явным ожиданием

Можно использовать канал без буфера и после `Shutdown` прочитать результат **в ветке сигнала**:

```go
case <-signalCtx.Done():
    shutdownErr := server.Shutdown(shutdownCtx)
    serveResult := <-serveErr // Читаем и при ошибке Shutdown, чтобы отпустить отправителя.
    if shutdownErr != nil {
        return fmt.Errorf("shutdown HTTP server: %w", shutdownErr)
    }
    if !errors.Is(serveResult, http.ErrServerClosed) {
        return fmt.Errorf("serve HTTP: %w", serveResult)
    }
```

Тогда отправка встретится с чтением, и горутина завершится. В ветке `case err := <-serveErr` результат уже получен; второй раз читать канал там нельзя. Для текущего приложения буфер на одно значение даёт более простой путь, если проверка результата после штатного `Shutdown` не нужна.

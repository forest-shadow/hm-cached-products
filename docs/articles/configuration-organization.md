# Организация конфигурации приложения и пакетов

Для текущего проекта удобно хранить структуры настроек, загрузку, значения по умолчанию и валидацию в `internal/config`. Выделять собственный конфиг компонента стоит тогда, когда компоненту нужна самостоятельность: несколько потребителей, повторное использование или независимые правила настройки.

Примеры ниже показывают варианты организации. Они не означают, что все описанные проверки и API уже реализованы в проекте.

## Секции конфигурации

Параметры логгера удобно размещать в отдельной секции рядом с `app` и `http_server`:

```yaml
app:
  name: "cached-products"
  env: "local"

logger:
  level: "debug"
  format: "console"

http_server:
  addr: ":8080"
```

`app` описывает приложение: имя, версию, окружение. Секции компонентов содержат параметры их работы. Если формат логов по умолчанию зависит от `app.env`, эту зависимость можно разрешить при подготовке конфигурации. Для этого не требуется вкладывать `logger` в `app`.

Расположение секции в YAML и владелец Go-типа — отдельные решения. Секция `logger` может оставаться на верхнем уровне и после переноса типа конфигурации в пакет логгера.

## Централизованный пакет `internal/config`

В одном приложении с общим жизненным циклом компонентов практична такая структура:

```text
internal/config/
  config.go   # Общая структура, загрузка и общая валидация
  app.go      # AppConfig и его валидация
  env.go      # AppEnv
  http.go     # HTTPServerConfig и его валидация
  logger.go   # LoggerConfig, LogLevel, LogFormat, defaults и валидация
```

Общая структура объединяет настройки:

```go
type Config struct {
    App        AppConfig        `mapstructure:"app"`
    Logger     LoggerConfig     `mapstructure:"logger"`
    HTTPServer HttpServerConfig `mapstructure:"http_server"`
}
```

Пакет `config` читает YAML и переменные окружения, преобразует значения в типы, применяет defaults и проверяет согласованность настроек. Общий `Validate` должен вызывать проверки соответствующих секций: наличие метода `LoggerConfig.Validate` само по себе не включает его в загрузку.

Удобный порядок подготовки: загрузить значения, разрешить defaults с учётом окружения, проверить итоговую конфигурацию, затем создавать компоненты. Ошибочное явно заданное значение должно приводить к ошибке, а не молча заменяться значением по умолчанию.

Конструктор логгера преобразует подготовленные параметры в настройки Zap и создаёт логгер. Ошибки открытия файла или инициализации вывода относятся к созданию компонента; одной проверки конфигурации для их обнаружения недостаточно.

Для такого варианта допустимо, что `zaplogger` принимает `config.LoggerConfig`. Пакет `config` при этом не импортирует `zaplogger` и не оперирует типами Zap. В `main` передаются только необходимые компоненту настройки.

## Когда централизованный вариант становится неудобным

| Ситуация | Что начинает мешать |
| --- | --- |
| Логгер нужен другому сервису или отдельному модулю | Его зависимость от конфигурации конкретного приложения тянет чужие типы и зависимости загрузчика. |
| Появляются API, worker и CLI | Общая структура обрастает условными правилами обязательности, хотя приложения используют разные наборы компонентов. |
| Компонент развивается как самостоятельная библиотека | Его публичный API и допустимые настройки приходится менять через пакет конфигурации одного приложения. |
| Проверка настроек требует знаний конкретной реализации | Возникает соблазн импортировать реализацию в `config`, хотя реализация уже зависит от `config`; это приводит к циклу импортов. |
| Компонент получает весь `AppConfig` ради одного решения | Зависимость от приложения расширяется; например, логгер узнаёт об окружениях только ради выбора формата. |

Несколько исполняемых приложений сначала могут потребовать разделить их корневые конфиги. Это не обязывает немедленно переносить каждый тип в свой компонент.

Само количество секций не определяет момент переноса. Важнее зависимости, разные потребители и то, кто отвечает за смысл параметров.

## Конфигурация внутри самостоятельного пакета

Если логгер становится самостоятельным компонентом, он может объявлять собственные `Config`, `Level`, `Format` и проверку допустимых сочетаний. Тогда приложение зависит от API логгера, а логгер не зависит от `internal/config` приложения.

Конфигурация приложения по-прежнему отвечает за источники значений и правила окружения. Например, она выбирает `console` для локального запуска и `json` для production, а конструктор логгера получает уже выбранный формат.

Возможны два способа связать настройки приложения и компонента:

- Включить `logger.Config` непосредственно в корневой конфиг, если его структура подходит для декодирования и не требует зависимостей от загрузчика внутри пакета логгера.
- Оставить отдельный `config.LoggerConfig` для входных данных и явно преобразовывать его в `logger.Config` при сборке приложения. Это полезно, если схема YAML и API компонента отличаются или должны изменяться независимо.

Во втором случае два типа имеют разные роли: один описывает внешние настройки приложения, другой — параметры компонента. Если роли полностью совпадают, отдельный тип и преобразование могут оказаться лишними.

Валидация тоже распределяется по ответственности:

- Конфигурация приложения проверяет источники, обязательные поля и связи между секциями.
- Пакет компонента проверяет собственные ограничения, чтобы его можно было безопасно создавать из любого вызывающего кода. Такую проверку можно выполнять в конструкторе.
- Сборка приложения разрешает зависимости от окружения и передаёт готовые параметры компонентам.

Общие правила компонента следует вызывать повторно через его API, а не копировать в загрузчик. При этом локальные defaults самого компонента могут оставаться внутри пакета, если они не зависят от политики приложения.

## Роль `pkg` и `internal`

Папка `pkg` сама по себе не делает компонент самостоятельным. Собственный конфиг оправдан его назначением и потребителями. Пакет внутри `internal` тоже может обслуживать несколько приложений репозитория и иметь собственный `Config`.

Если пакет планируется использовать из другого репозитория, ему нужен доступный для внешнего импорта путь: ограничения Go для `internal` не позволяют произвольно импортировать такие пакеты извне. Размещать публичный пакет именно в `pkg` при этом необязательно.

Для текущего приложения достаточно централизованного `internal/config`. Переносить настройки в компонент стоит при появлении конкретной потребности в независимости, сохраняя загрузку YAML, переменные окружения и политику окружений на стороне приложения.

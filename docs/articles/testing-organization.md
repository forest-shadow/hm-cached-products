# Организация тестирования

## Основной принцип

Каждый тест или измеряемый сценарий начинается с известного состояния данных, кэша и времени. Ожидаемый результат должен вычисляться из подготовленных данных, а не зависеть от того, когда в прошлом была применена миграция.

Это особенно важно для `GET /products/{id}/stats`: записи `product_views.viewed_at` со временем выходят из запрашиваемого окна. `products.updated_at` и сроки жизни записей кэша также влияют на проверки свежести и инвалидации.

Миграция `00002_create_seed_products.sql` даёт удобные примеры для ручной разработки. Её данные с `now()` не должны быть единственным источником ожидаемых значений в автоматических тестах.

## Данные и время

1. Перед каждым тестом подготовить только нужные товары, просмотры и, когда появится outbox, события. Для них зафиксировать ожидаемые значения и версии.
2. Использовать одну опорную точку времени `as_of` для создания временных данных и проверки результата. В модульных тестах передавать управляемые часы. В интеграционных тестах согласовать время приложения и SQL: если запрос использует `now()` PostgreSQL, одних управляемых часов в Go недостаточно. Удобный вариант — передавать `as_of` в запрос явно.
3. Для статистики определить поддерживаемые окна и правило границы окна (`>=` или `>`). Проверять пустой результат, попадание внутрь окна и просмотры по обе стороны границы.
4. Очищать или изолировать записи Redis и локального L1 между тестами. Проверять TTL, промах и инвалидацию на известных ключах; результат одного теста не должен зависеть от прогрева в другом.
5. Не делить изменяемые фикстуры между параллельными тестами. Использовать отдельную БД или схему и пространство ключей Redis либо выполнять такие тесты последовательно с очисткой состояния.

## По видам проверок

| Вид | Подготовка и изоляция |
| --- | --- |
| Модульные | Управляемые часы, подставные хранилища и кэши; контейнеры не нужны. |
| Интеграционные | Поднять PostgreSQL и Redis для набора тестов, применить схему, перед тестом создать его фикстуры и обеспечить очистку или изоляцию после него. Если worker работает через другое соединение, откат транзакции теста сам по себе не изолирует его работу. |
| Конкурентные | Подготовить один известный ключ и счётчик загрузок из PostgreSQL; одновременно запустить запросы, затем проверить число загрузок и итоговое значение. |
| Нагрузочные и сравнительные | Перед каждым прогоном восстановить одинаковый набор данных и распределение запросов. Отдельно измерять холодный и прогретый кэш; сбрасывать состояние кэша только для холодного прогона. Время подготовки данных не включать в измерение. |
| Отказы | Начать с известного состояния, внести отказ, проверить поведение и метрики, затем восстановить зависимость и проверить возврат к норме. |

Не требуется поднимать весь стенд заново перед каждым тестом. Достаточно гарантировать одинаковое исходное состояние и отсутствие влияния соседних тестов. Для повторяемого сравнения baseline и версии с кэшем использовать одинаковые данные, профиль нагрузки и критерии завершения прогона.

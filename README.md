# Cached Products

Учебный Go-проект для HTTP API продуктов с кешированием.

Цель проекта: показать пользу кэша на цифрах, при помощи сбора метрик

## Локальный запуск

```sh
cp env.example.yml env.local.yml
go mod download
APP_ENV=local go run ./cmd/api
```

Dev Tools: Air, Task и Goose закреплены в `go.mod` и запускаются через `go tool`; глобальная установка не требуется.

Для разработки с автоматической пересборкой:

```sh
go tool task dev:start
```

## Ручная проверка API в Postman

Импортируй [коллекцию](docs/cached-products.postman_collection.json) через **Import** в Postman.
В переменных коллекции укажи `base_url` (по умолчанию `http://localhost:8080`); отдельный environment не нужен.
API должен быть запущен с применёнными миграциями.

Выполняй запросы сверху вниз: `Health` → `Products` → `Statistics` → `Validation errors` → `Cleanup`.
Коллекция автоматически сохраняет ID и версию созданного товара, проверяет обновление и конфликт версий, статистику и ошибки валидации.
В папке `Cleanup` тестовый товар удаляется, затем проверяются ответы `404`. Весь сценарий можно запустить через Collection Runner; для повторного прогона начинай с создания нового товара.

## Конфигурация

Обязательная переменная `APP_ENV` выбирает файл `env.<APP_ENV>.yml`. Допустимые окружения: `local`, `development`, `staging`, `production`.

YAML-файл необязателен, если обязательные настройки переданы через окружение:

```sh
APP_ENV=local APP_APP_NAME=cached-products go run ./cmd/api
```

Таймауты HTTP-сервера задаются в секции `http_server` значениями Go duration (`500ms`, `5s`, `1m`):

```yaml
http_server:
  addr: ":8080"
  read_timeout: 0s
  read_header_timeout: 5s
  write_timeout: 0s
  idle_timeout: 60s
  shutdown_timeout: 10s
```

Здесь показаны значения по умолчанию. Их можно переопределить через окружение, например `APP_HTTP_SERVER_READ_HEADER_TIMEOUT=3s` или `APP_HTTP_SERVER_SHUTDOWN_TIMEOUT=15s`.
`read_timeout` ограничивает чтение всего запроса, включая тело; `read_header_timeout` — чтение заголовков; `write_timeout` — запись ответа; `idle_timeout` — ожидание следующего запроса в keep-alive соединении.
Для `read_timeout` и `write_timeout` значение `0s` отключает ограничение. Для `read_header_timeout` и `idle_timeout` значение `0s` использует `read_timeout`. Отрицательные значения запрещены, а `shutdown_timeout` должен быть больше нуля.

При `SIGINT` или `SIGTERM` сервер прекращает принимать новые соединения и ждёт завершения активных запросов в пределах `http_server.shutdown_timeout` (по умолчанию 10 секунд). Air отправляет `SIGINT` и даёт процессу до 15 секунд на завершение; при увеличении `shutdown_timeout` нужно согласовать с ним `kill_delay` в `.air.toml`.

# Требования проекта

## Функциональные требования

Реализуй HTTP API:
- `POST /products` — создать товар;
- `GET /products/{id}` — получить товар;
- `PUT /products/{id}` — изменить товар;
- `DELETE /products/{id}` — удалить товар;
- `GET /products/{id}/stats` — получить тяжёлую агрегированную статистику;
- `GET /health` — проверить состояние процесса;
- `GET /metrics` — отдать метрики Prometheus.

Источник истины — PostgreSQL. Redis используется как общий кэш L2. Дополнительно можно добавить локальный L1 для карточек товара.

## Схема данных

Минимальные таблицы:

```sql
CREATE TABLE products (
    id          BIGSERIAL PRIMARY KEY,
    name        TEXT NOT NULL,
    price       BIGINT NOT NULL CHECK (price >= 0),
    version     BIGINT NOT NULL DEFAULT 1,
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE product_views (
    product_id  BIGINT NOT NULL REFERENCES products(id),
    viewed_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Версия товара поможет защититься от записи старого значения поверх нового.

## Правила кэширования (Caching Rules)

Карточка товара:
- ключ: `product:v2:{id}`;
- TTL: 5 минут со случайным разбросом;
- стратегия: Cache-Aside;
- инвалидация: удаление после успешного изменения;
- при ошибке Redis: ограниченное обращение к PostgreSQL;
- для отсутствующего товара: отрицательное значение на 15–30 секунд.

Статистика:
- ключ: `product-stats:v1:{id}:{window}`;
- TTL: 30–60 секунд;
- объединение одновременных загрузок;
- допустим возврат немного устаревшего значения при медленном источнике.

## Этапы реализации проекта

### Этап 1. Исходная версия без кэша (Baseline)

Сначала реализуй сервис только с PostgreSQL. Измерь:
- p50, p95 и p99;
- число запросов к базе;
- занятые соединения;
- загрузку CPU;
- пропускную способность.

Это исходная точка. Без неё нельзя доказать, что кэш помог.

#### Сравнение обновления с `FOR UPDATE` и проверкой версии без outbox

До добавления outbox сравни две реализации одного контракта `PUT`:
- предварительное чтение `SELECT … FOR UPDATE`, проверка `expected_version` и обновление товара в одной транзакции;
- атомарный `UPDATE … WHERE id = … AND version = expected_version` без предварительного захвата строки.

В обеих реализациях сохрани одинаковые правила проверки версии, ответов `404` и `409`, изменения `version` и `updated_at`, а также обработки запроса с прежними значениями. Проверь, что из двух конкурентных запросов с одной версией и разными новыми значениями только один изменяет товар.

Сними отдельные профили нагрузки:
- каждый клиент обновляет свой товар — без конкуренции за строку;
- клиенты обновляют небольшой общий набор товаров — умеренная конкуренция;
- все клиенты обновляют один товар — высокая конкуренция.

Клиент читает версию из PostgreSQL через `GET`, затем меняет поле и отправляет `PUT`. В основном сравнении не повторяй запросы после `409`; стоимость повторов можно исследовать отдельно.

Измерь успешные изменения в секунду, p50/p95/p99 отдельно для успешных `PUT` и конфликтов, долю `409`, тайм-аутов и внутренних ошибок, SQL-вызовы на попытку и успешное изменение, занятые соединения и ожидание пула. Дополнительно измерь задержку всей операции `GET → PUT`; укажи, включены ли запросы чтения версии в подсчёт SQL.

Зафиксируй версии приложения и PostgreSQL, ресурсы стенда, настройки пула, уровень изоляции и границы транзакций. Используй одинаковые начальные данные и профиль нагрузки, прогрев и ступенчатое увеличение интенсивности; выполни не менее пяти измерительных прогонов каждого варианта, чередуя их порядок. Сохрани результаты и разброс между прогонами в `docs/`, затем выбери реализацию для дальнейшего baseline.

Условный `UPDATE` тоже блокирует изменяемую строку. Проверяй гипотезу о стоимости дополнительного запроса и более раннего захвата блокировки, не предполагая заранее победителя. Если один вариант использует автоматическую транзакцию, а другой явные `BEGIN` и `COMMIT`, учитывай это в выводах как часть стоимости реализации.

### Этап 2. Redis и ленивое кэширование (Cache-Aside)

Добавь:
- клиент Redis с предельными сроками;
- пространство имён и версию ключа;
- сериализацию;
- TTL;
- попадания, промахи и ошибки;
- удаление при записи.

### Этап 3. Защита от лавины запросов (Cache Stampede Protection)

Добавь объединение загрузок одного ключа. Проверь, что сто параллельных промахов одного товара создают одну или небольшое ограниченное число загрузок из PostgreSQL.

Локальный `singleflight` защищает только один экземпляр приложения. Запусти несколько экземпляров и сравни результат. Для межузловой защиты можно использовать короткую распределённую блокировку, но только с ограничением ожидания и безопасным резервным поведением.

### Этап 4. Инвалидация через события (Event-Driven Invalidation)

Товар и событие записываются в PostgreSQL одной транзакцией. Отдельный worker читает outbox и передаёт событие обработчику, который удаляет ключи Redis. Внешний брокер здесь не используется.

Проверь:
- повторную доставку;
- событие после более новой версии;
- временную недоступность Redis;
- повторную обработку после перезапуска;
- рост задержки инвалидации.

#### Повторное сравнение обновления после добавления outbox

Повтори сравнение двух реализаций из этапа 1: теперь каждая должна атомарно сохранять изменение товара и соответствующее событие outbox в одной явной транзакции. Правила API и создания событий должны совпадать.

Для сопоставимости с первым экспериментом отключи кэш и worker в обоих вариантах. Перед каждым прогоном обеспечь одинаковое начальное состояние товаров и outbox; зафиксируй одинаковые индексы и настройки БД. Работу с включёнными кэшем и worker проверяй отдельно как полный сценарий сервиса.

Повтори профили без конкуренции и с одним популярным товаром при небольшой нагрузке и около предела, найденного на этапе 1. Используй прежнюю методику повторов и те же метрики; отдельно учитывай SQL-вставку события. Проверь, что конфликт не создаёт событие, а ошибка записи события откатывает изменение товара.

Сохрани результаты рядом с замерами этапа 1. Сравни стоимость каждого варианта до и после outbox и изменение разницы между ними: дополнительная запись увеличивает работу внутри транзакции и может изменить преимущество выбранного подхода. Укажи ограничения выводов для сценария с остановленным worker.

### Этап 5. Локальный кэш первого уровня (L1 Cache)

Добавь небольшой локальный кэш поверх Redis. Сравни:
- задержку;
- сетевой трафик;
- память процесса;
- долю попаданий L1 и L2;
- свежесть данных между экземплярами.

Инвалидация должна очищать оба уровня или использовать достаточно короткий TTL L1.

### Этап 6. Проверка отказов (Failure Testing)

Проверь сценарии:
- Redis отключён;
- Redis отвечает медленно;
- PostgreSQL отвечает медленно;
- пул соединений исчерпан;
- кэш очищен перед пиком;
- одновременно истекает TTL популярных ключей;
- один экземпляр приложения перезапущен;
- событие инвалидации потеряно или задержано.

Для каждого сценария зафиксируй ожидаемый результат и метрики.

- `cache_fallback_total{cache,result}`;
- число запросов к PostgreSQL;

- занятые соединения;
- память и GC процесса Go;
- `used_memory`, `evicted_keys` и задержка команд Redis.

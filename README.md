# Cached Products

Учебный Go-проект для HTTP API продуктов с кешированием.

Цель проекта: показать пользу кэша на цифрах, при помощи сбора метрик

## Локальный запуск

```sh
cp env.example.yml env.local.yml
go mod download
APP_ENV=local go run ./cmd/api
```

Dev Tools: Air, Task и Goose закреплены в `go.mod` и запускаются через `go tool`; глобальная установка не требуется.

Для разработки с автоматической пересборкой:

```sh
go tool task dev:start
```

## Конфигурация

Обязательная переменная `APP_ENV` выбирает файл `env.<APP_ENV>.yml`. Допустимые окружения: `local`, `development`, `staging`, `production`.

YAML-файл необязателен, если обязательные настройки переданы через окружение:

```sh
APP_ENV=local APP_APP_NAME=cached-products go run ./cmd/api
```

При `SIGINT` или `SIGTERM` сервер прекращает принимать новые соединения и ждёт завершения активных запросов до 10 секунд. Air отправляет `SIGINT` и даёт процессу до 15 секунд на завершение.

# Требования проекта

## Функциональные требования

Реализуй HTTP API:
- `POST /products` — создать товар;
- `GET /products/{id}` — получить товар;
- `PUT /products/{id}` — изменить товар;
- `DELETE /products/{id}` — удалить товар;
- `GET /products/{id}/stats` — получить тяжёлую агрегированную статистику;
- `GET /health` — проверить состояние процесса;
- `GET /metrics` — отдать метрики Prometheus.

Источник истины — PostgreSQL. Redis используется как общий кэш L2. Дополнительно можно добавить локальный L1 для карточек товара.

## Схема данных

Минимальные таблицы:

```sql
CREATE TABLE products (
    id          BIGSERIAL PRIMARY KEY,
    name        TEXT NOT NULL,
    price       BIGINT NOT NULL CHECK (price >= 0),
    version     BIGINT NOT NULL DEFAULT 1,
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE product_views (
    product_id  BIGINT NOT NULL REFERENCES products(id),
    viewed_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Версия товара поможет защититься от записи старого значения поверх нового.

## Правила кэширования (Caching Rules)

Карточка товара:
- ключ: `product:v2:{id}`;
- TTL: 5 минут со случайным разбросом;
- стратегия: Cache-Aside;
- инвалидация: удаление после успешного изменения;
- при ошибке Redis: ограниченное обращение к PostgreSQL;
- для отсутствующего товара: отрицательное значение на 15–30 секунд.

Статистика:
- ключ: `product-stats:v1:{id}:{window}`;
- TTL: 30–60 секунд;
- объединение одновременных загрузок;
- допустим возврат немного устаревшего значения при медленном источнике.

## Этапы реализации проекта

### Этап 1. Исходная версия без кэша (Baseline)

Сначала реализуй сервис только с PostgreSQL. Измерь:
- p50, p95 и p99;
- число запросов к базе;
- занятые соединения;
- загрузку CPU;
- пропускную способность.

Это исходная точка. Без неё нельзя доказать, что кэш помог.

### Этап 2. Redis и ленивое кэширование (Cache-Aside)

Добавь:
- клиент Redis с предельными сроками;
- пространство имён и версию ключа;
- сериализацию;
- TTL;
- попадания, промахи и ошибки;
- удаление при записи.

### Этап 3. Защита от лавины запросов (Cache Stampede Protection)

Добавь объединение загрузок одного ключа. Проверь, что сто параллельных промахов одного товара создают одну или небольшое ограниченное число загрузок из PostgreSQL.

Локальный `singleflight` защищает только один экземпляр приложения. Запусти несколько экземпляров и сравни результат. Для межузловой защиты можно использовать короткую распределённую блокировку, но только с ограничением ожидания и безопасным резервным поведением.

### Этап 4. Инвалидация через события (Event-Driven Invalidation)

Товар и событие записываются в PostgreSQL одной транзакцией. Отдельный worker читает outbox и передаёт событие обработчику, который удаляет ключи Redis. Внешний брокер здесь не используется.

Проверь:
- повторную доставку;
- событие после более новой версии;
- временную недоступность Redis;
- повторную обработку после перезапуска;
- рост задержки инвалидации.

### Этап 5. Локальный кэш первого уровня (L1 Cache)

Добавь небольшой локальный кэш поверх Redis. Сравни:
- задержку;
- сетевой трафик;
- память процесса;
- долю попаданий L1 и L2;
- свежесть данных между экземплярами.

Инвалидация должна очищать оба уровня или использовать достаточно короткий TTL L1.

### Этап 6. Проверка отказов (Failure Testing)

Проверь сценарии:
- Redis отключён;
- Redis отвечает медленно;
- PostgreSQL отвечает медленно;
- пул соединений исчерпан;
- кэш очищен перед пиком;
- одновременно истекает TTL популярных ключей;
- один экземпляр приложения перезапущен;
- событие инвалидации потеряно или задержано.

Для каждого сценария зафиксируй ожидаемый результат и метрики.

## Метрики проекта (Project Metrics)

Минимальный набор:
- `cache_requests_total{cache,result}`;
- `cache_operation_seconds{cache,operation}`;
- `cache_source_loads_total{cache,result}`;
- `cache_invalidation_total{cache,result}`;
- `cache_invalidation_lag_seconds`;
- `cache_fallback_total{cache,result}`;
- число запросов к PostgreSQL;
- длительность запросов к PostgreSQL;
- p95 и p99 HTTP-запросов;
- занятые соединения;
- память и GC процесса Go;
- `used_memory`, `evicted_keys` и задержка команд Redis.
